# 升级部署与验收

## 启动与切换

1. 新建演示环境按 [README](../README.md) 启动。已有环境先备份，按顺序执行尚未应用的 SQL 迁移。以独立数据库账号部署指南和核心，指南账号的授权范围为 `guide` 表。
2. 把 `deploy/nacos` 下的 YAML 发布到目标环境的 Nacos namespace 和 `DEFAULT_GROUP`。Compose 会在 `community-demo` 自动创建缺少的配置。Redis、MySQL、JWT 和服务凭据通过环境注入。除前端和网关入口外，服务端口由私网承载。
3. 在同一切换窗口启用公开指南路由及后台指南代理。网关传递原路径、Cookie 和 `X-Trace-Id`。代理链只有配置在 `GATEWAY_TRUSTED_PROXIES` 的直接对端才可信。Compose 中 Nginx 先用实际对端地址覆盖转发头。
4. 升级完成后开启 `AUDIT_OUTBOX_ENABLED` 和 `AUDIT_PROCESSING_ENABLED`。先准备审核主题与死信主题。Compose 中由核心服务自动创建，均为三个分区，单副本。

## 验收步骤

| 场景 | 操作与应观察到的结果 |
| --- | --- |
| 原版基线 | 在原版独立实例创建同一批演示数据。登录，发布和下架指南，上传一份材料，提交申请、初审、复审和查询进度。设置 `API_BASE` 指向原版的 `/api`，运行 `node deploy/probe-guide.mjs 20`，记录 P95。原版公开指南每次成功请求都执行一次列表查询。 |
| 服务发现 | 从 Nacos 查询 `community-guide` 的实例列表。运行 `node deploy/probe-guide.mjs 20`，通过 `docker compose logs guide guide-replica` 中的请求 ID 对照两个实例。执行 `docker compose stop guide-replica`，待发现收敛后重复探测，剩余实例继续响应。执行 `docker compose start guide-replica` 恢复。 |
| 鉴权 | 匿名访问公开指南应成功，匿名写入应要求登录。使用普通账号与拥有 `guide:manage` 的账号分别尝试新增、发布和下架。通过网关访问 `/api/internal/guide` 和 `/api/actuator/health` 应得到 404。 |
| 缓存 | 清除单个列表数据键后发起并发探测。分别在两台指南实例上读取 `community.cache.db.query`，正常冷键窗口计数合计增加 1。热键探测期间查询计数不增长。空列表时检查 Redis 值为 `[]`。在一次慢回填中发布或下架指南，提交触发代数更新，旧回填不能再次写入数据键。对启用事项列表执行同样的变更验证。 |
| Redis 故障 | 停 Redis 后运行并发探测。公开列表受每进程最多 4 个并发回源的预算约束，超预算为 503。公开进度、提交和上传依赖限流状态，应返回 503。启动 Redis 后恢复探测。 |
| 可信 IP | 从同一连接地址重复请求合法格式的无效申请号 `AP2026111000000000` 和 `phoneLast4=0000`，每次变换自带的 `X-Forwarded-For` 和 `X-Community-Client-IP`。默认一分钟内超过 10 次应返回 429。使用真实测试申请和匹配的手机号后四位验证正常查询。 |
| Nacos 刷新 | 在 `community-core.yaml` 将进度限额由 10 改为 2。等待客户端更新并等待旧计数窗口过期，同一 IP 第三次请求应返回 429。修改指南缓存 TTL 后清除指南数据键，通过 Redis `TTL` 查看新设置加 0 至 60 秒抖动。验收结束后恢复配置。 |
| Kafka 补发 | 停 Kafka 后提交一次初审或复审，确认进度查询已反映新状态，并在 Outbox 查到事件。恢复 Kafka 后，Outbox 转为 `SENT` 并生成通知。 |
| 重复与失败 | 重投相同事件两次，按 `source_event_id` 查询只有一条通知。投递格式不合法的测试消息，确认有限重试后进入死信主题。修复原因后用原应用 ID 作为 Kafka 消息键，原样重放有效消息。 |

### 重跑业务回归

在独立测试库创建管理员并启动完整服务后，从项目根目录运行以下命令。脚本会创建测试申请、评价、预约和通知，请使用可重建的演示库。可选的 `SMOKE_EXPIRED_APPLY_NO` 指向一条已超时的测试申请，用于验证催办通知。

```powershell
$env:SMOKE_API_BASE = 'http://localhost:3000/api'
$env:SMOKE_FRONTEND_URL = 'http://localhost:3000'
$env:SMOKE_ADMIN_USER = '你的测试管理员账号'
$env:SMOKE_ADMIN_PASSWORD = '你的测试管理员密码'
node --test deploy/regression.mjs
```

脚本会验证登录与角色权限、会话、居民、指南、事项缓存、材料上传、申请审核、评价、预约、预警、通知、系统配置、统计和 Excel 下载。填写前端地址时也会检查 SPA 路由入口。审核通知检查同时适用于异步投递和同步回退配置。

### 查 Outbox 与重投

```sql
SELECT status, COUNT(*) AS total, MIN(created_at) AS oldest_utc
FROM application_event_outbox GROUP BY status;

SELECT event_id, application_id, status, attempts, next_attempt_at, last_error
FROM application_event_outbox WHERE status <> 'SENT' ORDER BY next_attempt_at;

SELECT source_event_id, COUNT(*) AS total
FROM notification WHERE source_event_id IS NOT NULL GROUP BY source_event_id;
```

`SENDING` 状态的 `next_attempt_at` 是当前租约到期时间，使用 UTC。投递达到 12 次失败会进入 `FAILED`。修复原因后将对应事件重新排队：

```sql
UPDATE application_event_outbox
SET status = 'PENDING', attempts = 0, lease_owner = NULL,
    next_attempt_at = UTC_TIMESTAMP(6), last_error = NULL
WHERE event_id = 'audit-v1-替换为审核记录ID' AND status = 'FAILED';
```

要重复投递一条已发送事件，可用 MySQL 查询 `CONCAT(application_id, CHAR(9), payload)` 获取单行原始内容，将该行作为标准输入交给：

```bash
docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka:9092 --topic community.application.audit.v1 \
  --property parse.key=true
```

死信主题为 `community.application.audit.v1.DLT`。回放使用原始消息键与原始 JSON，保留 `eventId`。消费重试次数和异常类型可从核心服务日志查询。

## 2026-11-10 联调记录

使用 JDK 17、MySQL 8.0.43、Nacos 2.3.2、Kafka 3.7.2 和独立的 Redis 5.0.14.1 Windows 兼容实例，启动原版及新版服务进程。使用相同指南数据和 20 并发，通过 MySQL 查询日志逐条统计。

| 公开指南场景 | 成功响应 | MySQL 列表查询 | P95 |
| --- | ---: | ---: | ---: |
| 原版直连 | 20/20 | 20 | 56.8 ms |
| 新版冷缓存，经网关 | 20/20 | 1 | 74.6 ms |
| 新版热缓存，经网关 | 20/20 | 0 | 54.0 ms |

- Nacos 注册了 `127.0.0.1:18082` 和 `127.0.0.1:18083` 两台指南实例。一次冷键探测的请求分别由两个实例各处理 10 次，日志中的请求 ID 样本为 `guide-probe-1794279068605-7` 和 `guide-probe-1794279068599-2`。停止一台实例后，网关返回 20/20 成功响应。
- Redis 停机并人为拉长数据库查询时，20 个公开指南请求有 8 个回源成功、12 个返回 503。进度、申请和附件入口返回 503。历史无过期计数键恢复到 60 秒有效期。
- Kafka 停机时初审和进度已提交，Outbox 进入重试。Broker 恢复后事件为 `SENT`，复审也生成通知。重复投递与重新领取过期租约后，每个审核事件仍只对应一条通知。无效 JSON 进入死信主题。强制 Outbox 写入失败后，申请仍为待受理，版本号保持提交后的值，审核记录和 Outbox 均为零条。
- 验证了新库初始化、旧版数据库连续执行两步迁移、管理员及普通账号的指南权限、登录 Cookie、附件上传和公开申请。9 项 Maven 测试、Node 22 前端生产构建和 Docker Compose 配置校验均通过。运行时联调通过独立进程完成。

### 提交前业务回归

8 组业务回归全部通过，并使用无头 Chrome 实际登录，验证居民入口及 19 个后台页面渲染。回归发现并修复了预约状态参数被绑定为整数、公开评价缺少手机号后四位时返回系统错误的问题，同时补齐公开申请手机号和评价评分的必填校验。本轮业务回归通过 Vite 代理接入网关，通知使用同步回退配置。Kafka 异步和 Nacos 故障场景的结果见上方联调记录。

## 回退

- 列表缓存发生故障时，将服务的 Nacos 配置项 `app.cache.enabled` 设为 `false`，查询仍受回源预算限制。指南回退时先停用新服务的写入，再切回上一个版本并清除指南缓存数据键。
- 需暂时恢复同步审核通知时，把 `AUDIT_OUTBOX_ENABLED` 设为 `false` 后重启核心。保持 `AUDIT_PROCESSING_ENABLED=true`，处理切换前已记录的事件。迁移结构和未发送事件保留，待发送事件沿用原事件 ID。
